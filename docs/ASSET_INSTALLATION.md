# Native asset installation

The iOS application accepts the host importer's `pt-ipad-assets-v1` manifest and extracted assets. The native verifier uses a compiled US asset catalogue, so changing the editable manifest or its evidence flags cannot authorize different data. `pathid_list_ps4.bin` may be absent if its manifest entry is also absent. The two archives are required.

Copy the complete directory into the app's `Documents/CUSA01127.incoming`, including `import-manifest.json`. Finish the transfer before requesting verification. The native function `pt::assets::PrepareUsInstallation(documents, callbacks)` verifies that staging directory and activates it as `Documents/CUSA01127`. It must run on a worker while the main thread pumps UIKit events; its callbacks execute on that worker. Cancellation is cooperative between bounded hash reads and before the transaction commits.

Each invocation hashes the files with CommonCrypto SHA-256 using a 256 KiB buffer. There is no persistent metadata-only verification cache. The manifest is limited to 1 MiB, and JSON depth, node counts, duplicate keys, types, numbers and escapes are checked. Files must have exact known lengths and digests, be regular files with one link, and have safe catalogue names. Symlinks, hard links, unknown directory entries and changing files are refused. Unknown host-audit fields are parsed but never used as filesystem paths. A bounded `source.txt` is allowed as inert provenance text.

First installation uses an exclusive rename. Replacement uses Apple's atomic directory exchange, then retains the old installation as `CUSA01127.previous`. Cancellation or backup-publication failure rolls the exchange back. A prior backup is never overwritten automatically. Preserve or explicitly remove that backup before another replacement. The installer never recursively deletes directories and never touches saves outside the asset directories. A native advisory lock prevents concurrent cooperating installation calls; the uploader must not change files during verification or activation.

A valid incoming installation can repair missing, truncated or oversized files in an existing owned installation. Ownership still requires a manifest matching the compiled catalogue and only allowed regular files with single links. The damaged prior directory is retained unchanged as the backup. A malformed manifest, unrelated file, save or symlink prevents replacement.

If incoming data is invalid and an existing installation passes full verification, the result remains playable with `staging_rejected=true` and an explanatory message. Invalid staging stays available for inspection. Results distinguish ready, activated, missing, invalid, cancelled, busy, I/O error and unsupported platform states. `result.ready()` is true only for verified ready or activated data. These states establish asset verification, not runtime or device gameplay acceptance.

The host test target is `pt_asset_install_test`. Its synthetic cases exercise multi-chunk hashing, optional data, JSON rejection, link and path safety, content mutation, concurrent lock ownership, cancellation and transactional rollback. They passed with AddressSanitizer and UndefinedBehaviorSanitizer. The same native verifier also accepted the existing authentic host import in read-only mode. The new translation unit compiled for iOS ARM64; an updated application build and device run are separate steps.
